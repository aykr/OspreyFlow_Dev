4. **Two verbs, accepted. The runner reads `SSH_ORIGINAL_COMMAND` once, matches it against the two exact shapes with an anchored pattern, and never passes any part of it to a shell.

## What the session builds (the owner's nine points, in his words, then what each needs)

1. **Server side: one install script, read and run by hand by the owner as root.** It creates a work folder and a runner. **The runner takes a git bundle on standard input, builds the candidate as `merge_slice.py` would (main with the slice merged in), runs `make -k ci` and `make test`, and prints one result: the candidate's tree hash, pass or fail, each failing check or test by name, and the time taken.**
   - *Read `merge_slice.py`'s gate exactly first* (how it makes the merge tree in a temporary folder from main and the slice's tip, the environment it gives `make -k ci` and `make test`: store ports pinned to 9, `UV_PROJECT_ENVIRONMENT`, `OSPREY_LANE`, the stack lease, the live step off, the copy of the gitignored hashed client-name list into the tree) and **reproduce its recipe, not a guess at it**; list in the report every step of the recipe and any you did not reproduce and why.
   - *The Mac has things the server does not.* **The hashed client-name list is gitignored and lives on the Mac only; the client-name check cannot run on the server without it, and sending it would move client-hash data off the Mac: that is the owner's decision, not the session's.** Default: do **not** send it; the runner reports those checks as `not run (no client-name list on this machine)`, never as passed. Likewise the Playwright snapshot images carry the platform in their names (`*-darwin.png`): a visual or contrast test whose snapshots exist only for macOS will fail on Linux for that reason; the runner reports it as a red like any other and the conductor's rerun on the Mac (point 8) settles it. Name every such Mac-only dependency you find.
   - *Toolchain:* the install script installs what the checks need (uv and the Python version the repository pins, Node 22, Chromium for Playwright) **from the places the repository already uses**; it reads before it runs (the owner reads it), opens no port and changes no DNS.
   - *Delivery shape:* a full run takes about an hour on the Mac (`make -k ci` about 26 minutes, `make test` about 11, plus the line's own suite). **Do not hold one SSH session open for it.** The forced command takes a verb: `run` (reads the bundle on stdin, starts the job detached, prints a job id and returns at once) and `result <id>` (prints the result, or `running` with the time so far); the Mac script polls. If you disagree, say why in the report.
   - *The bundle:* the server holds no repository credential (point 5), so the first run needs a full bundle of main and later runs an incremental one against the revisions the runner already holds in its **source copy** (a bare mirror in its work folder; the clean-up command removes it). The bundle carries main's tip and the slice's tip; the runner refuses a bundle whose tips it cannot resolve and says which.
2. **Access: one key, restricted on the server to that runner as a forced command. No shell, no port forwarding, no file copy.** The owner creates the key and puts it in place himself. **No key, address or host name is written into any file in the repository or any message** (this brief, the scripts, the tests, the result notes, your report): the install script prints the one `authorized_keys` line to add **with a placeholder for the key** and the options `command="<runner>",restrict` (which turns off the pty, port, agent and X11 forwarding); say in the report that `restrict` plus the forced command also leaves `scp` and `sftp` unavailable, and show the test or the sshd check that proves it. The Mac side reads the host and the key's file path from a setting **outside the repository** (`~/.ospreyflow/slice-line/demo-server.json`: its schema is written in the script's help; the file does not exist until the owner creates it). **A test fails if any file the session adds contains an IP address, a host-name-shaped string, a private-key block or a long base64 string** (planted: each, red).
3. **Mac side: one script the conductor runs for a verified slice.** It bundles, sends, waits (polls) and **writes the result as a note in the lanes folder** (`OspreyFlow_Build/process/lanes/v062/early_warning/<slice>-<tip first 8>.md`: the tree hash, pass or fail, the failing names, the time, the runner's version, the line "advice only; the Mac's merge run is the gate"). **It changes nothing in `merge_slice.py`, `stop_check.py` or the guard, and it writes no record the merge reads** (nothing under `~/.ospreyflow/slice-line/records/`; test by listing that folder before and after). It refuses to run for a slice that is not at `verified` in its records, and it never runs while no setting file exists (it says so in words). It is a line script the guard allows the conductor to run (it names its own path): say what the guard's allowlist needs (the owner adds it; you propose the exact line).
4. **Isolation on the server.** Every container, network and volume the runner starts **carries one prefix** (`osprey-early-`) **and its own ports, bound to loopback**. **It never stops, removes, restarts or renames anything it did not start.** Sixteen containers are running there now and **all of them are out of bounds**; the demo stays up. **If a fixed port or name makes that impossible, STOP and tell the owner which; do not work round it.**
   - *Measure first, before you write the runner:* search the repository for every test and fixture that starts a container or binds a port with a **fixed** name or port (compose project names such as `osprey-local-lite`, fixed host ports such as 2480, 5432, 6379, 8080, `make dev-up`, the stack lease script, testcontainers with fixed names; the memory notes say the throwaway test stack uses fixed ports). **List them in your report with file and line.** If any exist, the prefix-and-own-ports design cannot hold on the shared Docker daemon, **and you stop there and report them**; do not rename things in the repository's tests or add a flag the tests do not have. **Name, as options for the owner and not as something you build, the two structural ways round it:** (a) run the runner inside a separate network namespace with its own Docker daemon (rootless, its own socket and data root), so nothing it starts is visible to the demo's daemon at all; (b) run only the checks that need no containers. The owner chooses.
   - *Do not starve the demo:* run the candidate under a CPU and memory cap (`systemd-run --scope` with `CPUQuota` and `MemoryMax`, `nice` and `ionice`; the session proposes the numbers from the 16 processors, 62 GB and the 16 running containers' current use, read-only: `docker stats --no-stream` is allowed as a read) and a disk cap (the runner refuses to start under a free-space floor and removes its own work after each run).
5. **No GitHub.** The server holds no repository credential and pushes nothing anywhere: the runner has no remote, no token, no network call to a git host (a test or a read of the runner's own git config shows no remote and no credential helper).
6. **No new port opened to the internet, no DNS change, no change to any model's address, synthetic test data only.** The runner binds nothing but loopback; the install script's own output says what it opened (nothing); the tests the runner runs use the repository's synthetic fixtures only (the repository's own rule 9); **the runner never mounts any of the demo's volumes or data folders** (a test with a planted mount of a path outside the work folder: refused).

8. **How the conductor uses a result.** Green changes nothing. **On red, rerun the named failing check on the Mac before sending the slice back, because the server is a different kind of machine.
