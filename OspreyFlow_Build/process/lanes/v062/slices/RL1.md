## What (in this order; each with a test red first, a planted fault at the shape the code really sees: rule 15)

1. **The script, `OspreyFlow_Core/scripts/maintainer_manifest.py`.** `python -m scripts.maintainer_manifest --ref <commit-or-tag> --out <dir> [--maintained-under <rules-file>] [--check-areas]`. It reads **the tracked files at that ref and nothing from the working tree** (`git ls-tree -r -z` and `git cat-file --batch`, or `git archive` to a temporary folder: choose, justify), and writes two files: `maintainer-manifest.csv` (one row per file) and `maintainer-manifest.md` (a short summary, one row per folder). It can be run by hand at any ref.
2. **CSV columns, in this order:** `path`; `area`; `language`; `lines` (blank for a binary file); `bytes`; `is_test`; `is_generated`; `release_images`; and, only with `--maintained-under`, a last column `maintained_under`. Binary: a NUL byte in the first 8 KB. `language` from a table of extensions in the rules file (unknown extension: the word `unknown`, and the summary counts them). `lines` counts `\n` plus one for a last line without a newline. `is_test`: by path patterns in the rules file (names `*.test.ts`, `*.test.tsx`, `*.spec.ts`, folders `test/`, `tests/`, `keyboard/`, `a11y/`). **`is_generated` is decided from the repository's own evidence, never from a folder name:** (a) a header in the first lines (`AUTO-GENERATED`, `@generated`, `DO NOT EDIT`), or (b) a rules-file entry naming the file or folder **and the generator script and command, where the script exists in the tree at the ref** (for example `packages/schemas/generated/*.ts` by `packages/schemas/generate_ts.py` and `package.json`'s `schemas:generate`; `docs/pdf/*` by the document build, **whose generator is in `OspreyFlow_Build/tools` and so not in the tree: then the evidence is absent and the value is `no evidence in this tree`, not `yes`**). Values: `yes`, `no`, or `no evidence in this tree` (a file the scouts could not trace: `packages/schemas/release.schema.json`, `apps/workspace/src/shell/placesByRole.json`; say which of them you could trace). The summary explains the three values.
3. **The rules file, `OspreyFlow_Core/scripts/manifest_areas.toml`** (TOML, so the standard library reads it): areas by path pattern, first-match order stated, **"other" is not a catch-all: every folder placed in "other" is named in the rules**. **The areas (the owner's, agreed 21 November):** page service server (`apps/pages/server`, its views and scripts); GOV.UK tree (`apps/pages/tree-govuk` and the theme folder `packages/themes/govuk` when they exist); default tree (`apps/pages/tree-default`); drawing modules (`apps/pages/modules` and the drawing code when it exists); shared TypeScript (`packages/glass-shared`); design (`packages/design`); schemas (`packages/schemas`); React workspace (`apps/workspace`); Conduit (`services/api`); ingest (`services/ingest`, `connectors`); other service (`services/*` the rest, **including `services/laurium` with its paths shown: the owner's ruling is that the optional engine's paths are shown, not masked, and the list is exact**); adapters (`packages/adapters`); knowledge adapters (`packages/knowledge_adapters`); deploy (`deploy`, `.github`, the Dockerfiles' folders where not an app or service); tests (`is_test` files by their own area?
