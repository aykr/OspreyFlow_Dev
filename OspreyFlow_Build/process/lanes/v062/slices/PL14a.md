## The owner's request, and his three answers (they bind)

`scripts/refresh.py` (`ospreyflow start --build`) never rewrites `deployment.env` beyond the four model lines, but its last step rebuilds the search index. **A deployment whose `deployment.env` lacks a plain line the checkout's render writes keeps lacking it.** A test user hit this on a deployment made before 13 November: `OPENSEARCH_HOST` unset, the client fell back to `localhost:9200`. No line was added between v0.6.1 and main, so v0.6.x is not affected today; the next added line would be.

1. **The boundary (answer 1: A).** Refresh takes plain lines **only from what `harness.render._render_env` emits** and **never classifies a line by its name.** **The test fails closed: red if a key `_render_env` emits matches the secret name test (`_SECRET_KEY` in `OspreyFlow_Core/harness/apply.py`), or is not on a reviewed list.** A new render line therefore forces a human decision.
2. **Out of scope (answer 2: A).** The plain lines that **`apply` appends** are not touched: `OIDC_JWKS_URL`, `OIDC_TOKEN_EXCHANGE_URL`, `OIDC_TOKEN_EXCHANGE_CLIENT_ID`, `OIDC_ADMIN_USERS_URL`, `ARCADEDB_HOST`, `VALKEY_HOST`, and the managed-service hosts and ports from `managed_service_lines`. **Name them in your report as a remaining gap.**
3. **Add, never change (answer 3, changed from the owner's first wording).** Refresh **adds a render line that is missing.** It **does not change the value of a line that is already there**; the four model lines keep today's behaviour (`_MODEL_LINES` in `scripts/refresh.py`). **Where an existing line differs from the render, refresh names the keys (never the values) and says to run `ospreyflow apply`.** It never writes, changes or removes a secret, and never a line the operator added (a line the render does not emit). **`OSPREY_RELEASE_VERSION` is kept as it is** (`harness/apply.py` about line 1088 and `harness/fresh_only.py`: a deployment's release is the one it was rendered with): it is **not** named as differing.
