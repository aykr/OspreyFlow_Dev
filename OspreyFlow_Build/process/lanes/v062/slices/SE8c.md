# Slice SE8c · SE8 · Sign-ins are recorded by the product, with no change to any identity provider's configuration

- **Build id:** SE8 (every access, export and model call is attributable). The owner's ruling of 21 November 2026, in full: *sign-ins are recorded by the product, with no change to any identity provider's configuration: the page service at its sign-in callback and sign-out, and the Conduit the first time it sees a new session. An organisation's own sign-in service cannot be reconfigured by the product, so the design must not depend on it. Refused sign-in attempts stay in the identity provider's own log, and the guide says so.*
- **Dial setting:** balanced
- **Rounds limit:** the dial's (8)
- **After:** nothing hard. It adds a Conduit route and touches `apps/pages/server/` (IS5a0, running, also touches `apps/pages/server/`: **start this slice after IS5a0 merges, or merge main in before your final report and keep both**). It touches nothing under `apps/workspace` and no protected file.
- **Status of this brief:** written by the conductor on 21 November 2026 from the SE8 scout (read, not measured; **re-read every line**). **This is an identity and security build: a fault that records, logs or sends a token, a session cookie, a key or a password is never accepted; the SE key rules bind (synthetic tokens at run time; nothing secret in any record, log or message).**

## What exists (the scout's findings)

No record is written for a sign-in today. The Conduit resolves a bearer token to a principal in `OspreyFlow_Core/packages/principal_auth/__init__.py` (`PrincipalResolver.resolve_principal`, about lines 1593, 1679, 751; `services/api/auth.py` re-exports it); it logs warnings only. The page service's `/session/sign-in` (about `OspreyFlow_Core/apps/pages/server/app.ts` 181 to 212), `/session/callback` (217 to 255; `startSession` 158 to 177), `/session/sign-out` (257 to 264) write no audit row; refusals are `console.error` (149 to 150, 243 to 248) and **the refusal path's log includes the provider's error message text** (look at what it can contain). The workspace signs in client-side (`apps/workspace/src/auth/userManager.ts`); the guided install page has no person sign-in. The pages service has **no database of its own** (it keeps sessions in Valkey). The audit table is `audit_log` (`services/api/audit.py` about 45 to 54; writer `AuditWriter.record`, fails closed). Existing sign-in-related records: admin set/reset of a person's sign-in (`app.py` about 17767, 17985) and the Superset guest token (about 20098). Keycloak's own events are on but keep only first-login errors (`harness/keycloak_admin.py` about 600 to 605; `harness/realm.py` about 640). **The product must not depend on, or change, any identity provider's configuration.**

## What (in this order; each a test red first, planted faults at the shape the code really sees: rule 15)

1. **The Conduit records a new session the first time it sees one.** When `resolve_principal` (or the layer above it that every route passes through; find the one place every authenticated request goes) accepts a token for a session it has not seen, it writes one audit row `sign_in_seen` (name it consistently with `test_audit_kinds.py` and classify it): principal, time, **how the session is identified without recording the token**: use a stable non-secret session identifier the token carries (for example the `sid` or `jti` claim, or the token's issued-at plus subject), **never the token or any part of it that could be replayed; hash it with a per-deployment secret if the claim is secret-like, and say what you chose and why.** "The first time" needs a place to remember which sessions were seen: choose one that survives a restart of one Conduit replica and works with several replicas (the Valkey working-set the Conduit already uses, with a time limit as long as the token's life; or a table); say what happens when the store is unreachable (**fail open for the request, never block a sign-in because the record store is down, but write a loud log line without the token and count the miss; or fail closed? decide, justify, and test: the owner's rule for audit writes is fail closed; for this row the first sight of a session is not the person's action, so do not turn a store fault into locking people out: report the choice**). The record must not become an oracle (a refused or unknown token writes nothing and says nothing new).
2. **The page service reports its sign-in callback and sign-out to the Conduit.** After a successful callback (`startSession`) the page service calls a **new Conduit route** (an internal, authenticated one) to record `sign_in` (principal from the token the Conduit validates, with the page service's own client identity as the channel), and at sign-out `sign_out`. The route: authenticated by the person's own token (the page service already forwards it), so a caller can only record events for the identity of the token it holds and **can never record an event for another principal** (rule 4: access-control test with and without a token, with a token of another person, with an expired token, with the page service's own client credential alone: refused). It accepts no free text from the caller (an event kind from a closed list and nothing else), is rate-limited like the other write routes, and is idempotent for a repeated callback of one session. A sign-out after the token expired: the page service still deletes the session and records `sign_out` only if the token can be validated; otherwise it records nothing and logs without the token (say so). The page service's failure to reach the Conduit never stops a sign-in or sign-out (log, count, carry on); a test with the Conduit down.
3. **The workspace's client-side sign-in is covered by item 1** (the Conduit sees a new session); do not change the workspace (PL4 is running there). Say in your report which sign-in paths item 1 and item 2 cover and which are left, with the reason.
4. **Refused sign-in attempts stay in the identity provider's own log.** Nothing in the product records them (the provider's refusal never reaches the Conduit). Make the page service's refusal log line carry the reason **class** from a closed list and never the provider's message text (the scout found the provider's error message in the log: planted with a synthetic message containing a secret-shaped string at run time; red), and say in your report exactly where the guide must say "refused sign-in attempts are in your identity provider's own log" (the guides are DC1's and the administration guide's wording is a later slice: do not edit the guides; list the sentence and the place).
5. **No identity provider configuration changes:** `harness/realm.py`, `harness/keycloak_admin.py`, the realm exports and any provider setting are untouched; a test fails if the diff touches them (assert by reading the changed file list from `git diff`, or by reading the files' bytes against main in the test; say which).
6. **Rule 12:** a test fails if the Conduit stops recording a first-seen session (planted: remove the write); a test fails if the page service's callback stops calling the route (planted: remove the call); sign-out likewise. Per-route access-control tests (item 2). **A record never carries:** a token, any part of one, a cookie, a code, a state value, a client secret, a password, an address of the provider (synthetic values placed in each at run time; asserted absent from every audit column and every log line of each path).
7. **Report:** the session identifier chosen and why; where first-seen is remembered; the fail-open/closed choice and its test; the route and its tests; what is covered and what not; the sentence for the guide; any live test owed (Valkey, Postgres).
