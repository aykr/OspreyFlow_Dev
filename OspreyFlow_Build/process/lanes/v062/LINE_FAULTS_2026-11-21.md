6. **The merge's red-before step has no timeout, so one hung acceptance test holds the lock and the line for ever (found 21 November, 61 minutes lost on SE8a's merge).** `merge_slice.py` runs the slice's acceptance command against the base commit first (it must fail there: rule 15) and waits for it without a limit. The log stopped growing at 13:07; the merge was interrupted at 14:09. **Two fixes for the line-fix session:** (a) the red-before run gets a time limit (propose 15 minutes) after which it counts as red **and says so in the merge log** ("the acceptance command did not finish in N minutes at the base: counted as red"), and (b) the verifier's checklist asks whether every await in the acceptance test is bounded. Until fixed the conductor watches the log and ends such a run after 8 silent minutes, recording that it did.
8. **A note, not a fault (the first result from the demo server, 21 November; the owner's file 002): a verified slice sat in the queue with a conflict the line had not seen.** The early-warning run on DC1c (tip `229069b9`) found that it does not merge cleanly onto main: PL7a1's guide changes landed first, and both sides added version rows 2.30 to 2.33 to the administration guide's change table, with the four guide PDFs and `docs/pdf/manifest.json` conflicting beside it. **The line checks for a conflict with main only at merge, not when a slice is verified** (`merge_slice.py` about lines 866 to 884: at the start of `merge` it runs `git merge-tree --write-tree --name-only` on main and the tip and refuses, recording a finding, if files are named; `resume.py` about line 138 runs the same check when a slice is sent back; neither the verifier's pass nor the board does).
