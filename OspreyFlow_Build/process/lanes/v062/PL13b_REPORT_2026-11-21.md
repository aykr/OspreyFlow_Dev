# PL13b: OspreyFlow's own gateway image, the builder's record (21 November 2026)

What was built, what was measured, what the owner has to decide or apply, and which test fails if each invariant is
broken. No key, token or address is in this file: the keys of every run were made at run time, held in the shell and in
throwaway containers, and removed with them.

## First: what the owner must decide (the scan found a real fault in the pinned version)

1. **litellm 1.101.0 carries one HIGH the scan will not let a release past: CVE-2026-114612, "Privilege Escalation to
   Proxy Admin via Cross-Domain Reuse of the Salt Key"** (fixed in 1.101.3, 1.102.2 and later; the publisher's own image
   at the pinned digest carries it too, with 71 other fixable findings, 7 of them CRITICAL, in 23 packages). It is about the
   salt key the gateway holds, so it is a key-handling fault. The release workflow's trivy step (`--exit-code 1`, HIGH and
   CRITICAL, fixable) and the new `trivy-image-litellm` target stop on it. **Not fixed here, because the pin is the
   brief's and the frozen acceptance test holds `litellm==1.101.0`.** Measured for the owner, in scratch, not committed:
   the same folder with the one version changed to **1.101.3** builds (46 s warm), the build's gate passes, **trivy finds
   0 HIGH or CRITICAL**, the 24-call script gives the same 24 statuses as the pinned publisher image, and the repository's
   `test_model_gateway_live.py` (the key round trip and the usage test) passes against it. `litellm-proxy-extras` stays at 0.4.94
   (1.101.3 names the same), and the constraints file needs no other change. **Recommendation: a small follow-up slice
   moves 1.101.0 to 1.101.3** (the Dockerfile, the NOTICE, the label, the acceptance test's two constants), before release A
   and before patch 2b is applied. The other way is a `.trivyignore` entry with a reason and an expiry, which is the owner's file.
2. **No register row fails the owner's definition.** The two new bases are confirmed: the Wolfi base (MIT, read from the
   pinned image's own package database: the packages that make it declare MIT; Chainguard's recipes are Apache-2.0) and the
   uv image (Apache-2.0 by its own label; the project is MIT or Apache-2.0). **The register has no kind for a Python package or
   for the Prisma command line**, so `litellm` (MIT, PyPI record at 1.101.0, read in `deploy/litellm/NOTICE`) and Prisma
   (Apache-2.0 files, scout row 9) are recorded in the image's NOTICE and the product's NOTICE, not as rows. Adding a kind is
   PL11's tool and the owner's rule; not done.
3. **No ADR amendment was written** for "the gateway is OspreyFlow's own image" (it needs a reserved number,
   `spec/ADR_RESERVATIONS.md`). Suggested: an ADR-135 amendment citing the owner's ruling of 21 November 2026.

## The image

- Base: the publisher's own `cgr.dev/chainguard/wolfi-base@sha256:e624c5d5…` (both stages), `apk add bash openssl tzdata
  nodejs python-3.13 libsndfile` in the final stage, then **the base's package list unpinned and `apk upgrade`d** (found by the
  first scan: the base's `/etc/apk/world` holds every package at the exact version it was built with, so `apk upgrade` alone
  moved none of them and left zlib and the CA bundle at versions with fixes out). Final stage copies five paths from the builder.
- **Size 1.198 GB** (arm64, as measured here; the publisher's image is 1.182 GB). Runs as `10001:10001`. **Cold build 1 min 40 s**
  on this Mac (`docker build --no-cache --pull`), 18 s to 55 s with the cache.
- Built from PyPI's files and **never from the publisher's image**. The constraints file was made on 21 November 2026 by
  running the pinned publisher image once with no network (`--network none --entrypoint /app/.venv/bin/python`) and reading
  every installed distribution with `importlib.metadata` as `name==version`: 193 distributions; litellm,
  litellm-proxy-extras and the proprietary one left out; **15 packages raised by hand after the first scan** (aiohttp 3.14.4,
  anyio 4.14.2, certifi 2026.10.18, ddtrace 4.15.6, dnspython 2.9.2, filelock 4.2.1, fsspec 2026.6.0, mcp 1.30.0, oauthlib 4.0.1,

  0.1.0, which ddtrace 4.15.6 names). Each raise is within the ranges litellm and its extras declare (the resolver accepted it).
  The venv of the final image is the pinned image's, less the proprietary package, plus those 16 changes.
- **Build-time licence gate** (`licence_gate.py`, standard library only): reads every `*.dist-info/METADATA`, fails on the
  package by name, on any distribution declaring a proprietary licence (`License-Expression`, `License`, the classifier), on a

  builder's gate stopped the build naming it three ways (the package, `LicenseRef-Proprietary`, its folder); with the builder's
  own gate removed as well, the final stage's gate stopped it the same way. No image was made either time.
- **Trivy** (`--severity HIGH,CRITICAL --ignore-unfixed`, v0.76.1): first scan 59 findings in 17 packages; after the raises and
  the apk fix **1 finding: litellm 1.101.0, CVE-2026-114612 (HIGH)**, above. The publisher's image at the pinned digest: 72
  findings in 23 packages (7 CRITICAL).
- **The 24-call route script** (my own, equivalent to the scout's: its script was not kept; liveliness and readiness, no key

  tag from page 1 of that endpoint, which pages its answer; the script was changed to read the pages (the product's own reader

**Order the owner applies things in:** (1) patch 1, at any time; (2) patch 2a, before the slice merges; (3) the slice merges;
(4) the litellm decision (the follow-up slice, or an ignore entry with an expiry); (5) patch 2b; (6) a tag: the release workflow
builds, scans and signs the image (the first run needs ghcr.io to accept the new package, as every first run does: the images are
private until opened); (7) the release-notes sentence is the conductor's. **PL7d's diffs touch the same lines** (the matrix after
Superset's entry, the `OPTIONAL_OWNED_SERVICES` line, the target block): whichever the owner applies first, the other is written
again against the new main; patch 1 also edits `bundle.py` and `update.py`, which PL7d does not.

**What release A needs:** patch 1, patch 2a and patch 2b applied in that order with the litellm decision made, then the tag. **The next
refresh or apply of any deployment renders our image**; a render from source builds it, a pull render names an image no
registry holds until release A. The owner's deployment and the GOV.UK demo were not touched (no start, no stop, no render).
`refresh` leaves a deployment built from source alone (`"build" in wanted` is skipped), so it keeps the publisher's image until its next `apply`.

## Owed live tests (what only a live run shows)

The live step is off. Run here, by hand and not under a lease (a throwaway network of my own, no container on the owner's network or
ports): the key round trip and the usage test against the final image, the 24 calls. **Owed, because they could not or should not

(`conformance-model`, `conformance-model-vision`) against the image the patch builds (real Ollama and Whisper models); the Laurium
live tests (`test_laurium_key_live.py`, `test_laurium_reads_a_real_model_live.py`); the Bedrock route (no AWS); the release workflow
building the image for both platforms, scanning it as amd64 and signing it (the image was built and run here on arm64 only; the
constraints file was made from the arm64 layer, and the resolver accepted it for both); `ospreyflow images push` building it for
the managed platform (`linux/amd64`); the bundle exit test (`OSPREY_TEST_DIST_BUNDLE=1`, whose list of owned images now
holds the gateway and builds it from its own folder: edited, not run); and a full `ospreyflow start --build` of a deployment, which
means the owner's deployment or a lease.
