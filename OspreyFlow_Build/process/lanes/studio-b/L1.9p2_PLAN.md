## Found before planning (the code is the evidence)

- **Who reads.** `read_into_file` and `check_connection` are called only from `services/api/app.py`. The worker
  (`services.api.worker_main`) runs two job types, neither a connector read. So **the Conduit (`api`) alone** reads
  S3 and Athena, and gets the rows. (P7b gives `connector_hosts` to `api` and `worker`. That is P7b's and is not
  changed here; it is noted for the orchestrator.)
- **Account.** P7b: IRSA's one account (`secrets.irsa.service_account`) is shared by api, worker and report-sync, and
  is one IAM role. The read statements attach to that role (the brief: "the account the reading pod already has").
  Egress keeps the other two pods off the hosts; IAM alone does not. This is logged as a decision.
- **pyarrow and a wrong region, measured** (pyarrow 26.0.0, the real C++ SDK, against a local stub answering AWS's
  documented 301 `PermanentRedirect` and 400 `AuthorizationHeaderMalformed`): one request each, **never followed**.
  The error is `AWS Error UNKNOWN (HTTP status 301|400) …`, and on HeadBucket pyarrow adds its own "Looks like the
  configured region is … while the bucket is located in …". Today `refused_by_store` words these generically.

## Settings shape (item 1)

```yaml
cloud_platform:
  connector_sources:
    s3:
      - {bucket: synthetic-exports, region: eu-west-2, prefix: client-a/}
    athena:
      - workgroup: analysts
        region: eu-west-2
        databases: [visits]
        results_location: s3://synthetic-athena-results/out/   # required: IAM's Put is scoped to it
        table_locations: [s3://synthetic-lake/visits/]         # Athena reads these as the role; IAM only
```
