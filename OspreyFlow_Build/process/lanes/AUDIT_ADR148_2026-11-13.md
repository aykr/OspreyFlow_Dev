# Audit · ADR-148 and its amendments against cloud-platform `shape: poc` at v0.5.2 (13 November 2026)

Read-only, by an independent reviewer at the owner's request after the Superset miss. "v0.5.2" = main plus Superset and
report sync on Entra (the plan before the owner's 13 Nov evening scope, which adds OpenSearch-backed search and the
manifest). Inferred findings are marked so in the full report; this file keeps the summary and the orchestrator's
follow-ups. The full tables are in the orchestrator's session record of 13 Nov.

## Summary, most serious first

1. **Owner resolution is unavailable on Entra** (ADR-148 Am 8 p4, the orchestrator's ruling of 11 Nov; CARRIES 197,
   no target step). Every scheduled load, the run API (Airflow-triggered loads), screening refresh and the KYC sweep
   stop on this profile. The client page promises Airflow-triggered and scheduled loads (PAGE:231, 597).
2. **Laurium:** rendered by default, but no screen calls its review route (ADR-135 Am 9 p2); the page's "read
   documents with Laurium" is not delivered and no step plans a screen. No CARRIES row.
3. **OpenSearch was cut from poc by the orchestrator's ruling** (ADR-148 Am 5 p10); no pod reads OpenSearch in any
   shape. (Now in v0.5.2's scope, the owner's decision of 13 Nov.)
4. **Data safety:** the shared claim (published pipelines, model settings, key file) is in no backup set (P8
   deferred); RDS keeps 7 days of point-in-time restore against 35-day sets (Am 7 p10 cannot pair most sets); the
   decommission keeps the backups bucket and KMS key by default, against the page's record of destruction.
5. **Entra and the page:** the page offers an administrator fallback for unit and clearance that the code refuses
   (Am 8 p3), groups-to-roles mapping the code does not do (Am 6 p4), one app registration where two are needed
   (Am 8 p7); guests are refused (Am 6 p8); Entra has never met a real tenant (CARRIES 201). The spec-08 acceptance
   scenarios were replaced by R1's 28 checks without an ADR (inferred).

Also found: map providers added in Admin get no egress (d7, no row); volume encryption depends on the platform's
StorageClass, unchecked (d5); the egress "managed network" is the whole shared /16 (Am 1 i6); `bi.<host>` returns
with Superset and may fall outside the platform certificate (Am 1 i5); ModSecurity's body limit may cap uploads far
below 512 MiB (Am 1 i12); one IRSA role is shared by api, worker and report sync (CARRIES 189).

## Ruling 1's options, as put to the owner (13 November 2026) and ruled: option A

| Option | How | Rule 3 (never more than its owner has now) | Client creates in Entra | Size |
| --- | --- | --- | --- | --- |
| **A (ruled)** | Run as the owner's stored identity. Roles and disabled status are read live from Admin › People; clearance, unit and codes as at their last sign-in, refused if older than 24 hours | Yes. The same 24-hour rule already accepted | Nothing | ~1 day plus reviews |
| B | A service identity per schedule, with access copied at scheduling time | **No,** unless re-checked against the owner, which is A again | Nothing | ~1 day |
| C | Store each owner's Entra refresh token and use it at run time | Yes | A confidential client and Conditional Access exceptions | 2+ days; stored long-lived tokens; dies after ~90 days idle |
| D | A run identity registered in Admin | **No** | | |

A's known limit, stated with it: a schedule's run is refused once its owner has not signed in for 24 hours (for
example over a weekend), and the refusal must say so in true words. Reading the owner afresh from Microsoft Graph at
each run would lift that limit, but it needs a Graph application permission on the client's API registration, which
option A ruled out ("client creates nothing"). It is a separate decision for the owner, not part of A.
