== What could not be rehearsed, and why
`ospreyflow update` moves only to a signed release (find_release, a cosign-verified lock, GHCR pull).
main's head is no release, so the update itself cannot target it before v0.5.0 is tagged. Stood in:
v0.4.12 installed from the user repository's tag (422833c = from 964a2a9, its signed images), then the
same clone moved to `make publish-user-repo COMMIT=<head>`'s export (a commit "OspreyFlow — from <sha>"),
and the update's own steps run by hand: `ospreyflow backup` (v0.4.12's code), then update.py's files step
`python -m scripts.refresh --files-only`, then the code moved by `harness.apply --build`. Not exercised:
update's pull of v0.5.0's signed images, pin_images, verify_running, its rollback. OWED once v0.5.0 is
tagged: one real `ospreyflow update` from a fresh v0.4.12 on this server, before the owner's own.

== The CHANGELOG's upgrade steps, as proven (for docs)
- The seven one-off scripts run in the order: migrate_cases_to_one_dataset, migrate_branches_to_views,
  seed_target_models, make_home_cases, migrate_rules_to_datasets, migrate_sources, remark_alert_nodes;
  each `--dry-run` first; a second run changes nothing (all seven proven so).
- On a named deployment the container is `<name>-api-1` (osprey-upg-api-1); the scripts need no host
  environment.
- make_home_cases names datasets made by a seed or service account as needing an owner: give each one in
  Admin > Datasets > Change owner... It need not come before migrate_rules_to_datasets: a home case with
  no Author still takes the rule copies (run 1, Fixture Corp and Ledger).
- After migrate_rules_to_datasets, a whole-deployment rule's copies are drafts in each dataset's home
  case; an administrator must give someone Rule author (author_rules) before they can be tested and made
  live. A live case rule keeps running while its owner holds deploy_rules or author_rules (decision 13):
  check each rule's owner still holds one, in Admin > People.
- The update from v0.4.12, as proven on platform-b's d85f514 (run 4), with the checkout at v0.5.0:
  `ospreyflow backup --name <x>`; `ospreyflow apply --name <x>` (says the model keys are not yet moved);
  `ospreyflow update --name <x>`; `ospreyflow apply --name <x>` again (moves the keys into the gateway);
  then the seven scripts. A plain `ospreyflow update` from v0.4.12 refuses first, in those words,
  changing nothing. If an apply left the gateway unhealthy, `ospreyflow start --name <x>` recovers it.
- OWED after the tag: one real `ospreyflow update --name` from a fresh v0.4.12 on this server (the
  release's pull, pin, verify and rollback, and the lock's digests), before the owner's own.
