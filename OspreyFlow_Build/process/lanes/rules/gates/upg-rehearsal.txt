== What could not be rehearsed, and why
`ospreyflow update` moves only to a signed release (find_release, a cosign-verified lock, GHCR pull).
main's head is no release, so the update itself cannot target it before v0.5.0 is tagged. Stood in:
v0.4.12 installed from the user repository's tag (422833c = from 964a2a9, its signed images), then the
same clone moved to `make publish-user-repo COMMIT=<head>`'s export (a commit "OspreyFlow — from <sha>"),
and the update's own steps run by hand: `ospreyflow backup` (v0.4.12's code), then update.py's files step
`python -m scripts.refresh --files-only`, then the code moved by `harness.apply --build`. Not exercised:
update's pull of v0.5.0's signed images, pin_images, verify_running, its rollback. OWED once v0.5.0 is
tagged: one real `ospreyflow update` from a fresh v0.4.12 on this server, before the owner's own.
